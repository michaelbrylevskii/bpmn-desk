# Публикация

## Публичный репозиторий

[michaelbrylevskii/bpmn-desk](https://github.com/michaelbrylevskii/bpmn-desk) распространяет код по MIT, три заимствованных примера — по Apache-2.0 и символ иконки Lucide — по ISC. Происхождение схем закреплено в `examples/provenance.json`, лицензии включаются в дистрибутивы.

Публичная история начинается с одного root-коммита очищенных исходников. Прежняя локальная история разработки хранится отдельно и не отправляется в GitHub. В публичной истории нет прежних пользовательских схем. Кеши, traces, локальные пакеты и исходники конкретного пользователя не входят в Git или релиз.

## Проверки и сборки

Workflow `.github/workflows/build.yml` запускается на push основной ветки, pull request и вручную. Для Linux и Windows выполняются `npm ci`, настройка Electron/Chromium, `npm run check`, нативная упаковка, UI/Electron и официальный конвертер Flowable. Проверяются только встроенные схемы.

При успешной проверке Actions сохраняет AppImage и два EXE на 14 дней. При ошибке UI сохраняются диагностические результаты тестов на 7 дней. Пользовательские наборы в CI не подключаются; их отдельные прогоны остаются локальными.

## Выпуск новой версии

1. Обновить версию package/lock и добавить `docs/releases/<версия>.md`. Зафиксировать изменения отдельным коммитом; сообщения коммитов — на английском, документация — на русском.
2. Локально выполнить `npm run check`, `npm run package:linux`, `npm run test:e2e` и `npm run validate:flowable`. Проверить состав артефактов, лицензии и provenance. Windows требует отдельной проверки на своей ОС.
3. Отправить основную ветку и дождаться успешной матрицы GitHub Actions.
4. Создать тег `v<версия>` на проверенном коммите и отправить только этот тег. Push тега заново собирает и проверяет обе платформы, создаёт SHA256SUMS, загружает три дистрибутива в черновик release и публикует его после успешной загрузки.
5. Проверить опубликованные assets, их суммы и ссылку на запуск workflow. Локальные хеши из `docs/validation.md` могут отличаться от CI из-за временных меток упаковки; для конкретного релиза используются его SHA256SUMS.

Изменение версии без совпадающего тега или отсутствие release notes блокирует публикацию. Сборка electron-builder использует `--publish never`; загрузку выполняет отдельная задача workflow с GitHub CLI. Релиз не создаётся на pull request или обычном push ветки.

## Локальный запасной вариант

Если CI недоступен, можно отдельно собрать Linux и Windows штатными командами. Затем запустить `node scripts/release-manifest.mjs`, проверить файлы и SHA256SUMS и создать release через `gh release create` на опубликованном теге. В описании нужно прямо указать локальное происхождение сборок и реально выполненные проверки. Пользовательские кеши и весь рабочий каталог не загружаются.

## Границы проверки

EXE не подписаны. Автоматические проверки Windows Server не подтверждают ручную установку, удаление и ассоциации на Windows 10/11. macOS пока не поставляется. Актуальные результаты локальной проверки и аудит зависимостей: [validation.md](validation.md); решения: [ADR 0013](adr/0013-github-actions-release.md).
