# Публикация

## Release notes

- `docs/releases/<версия>.md` — русский источник.
- `.github/release-notes/<версия>.md` — английский публикационный текст.
- `node scripts/release-notes.mjs [версия]` — английский текст и русский перевод в закрытом `<details>`. По умолчанию берётся версия package.

Оба языка обязательны. Генератор сохраняет Markdown и используется для новых и существующих GitHub-релизов; перевод не копируется в несколько файлов.

## Выпуск

1. Обновить package/lock, оба текста release notes и соответствующие изображения/возможности README.
2. Выполнить [проверки](development.md), проверить состав, provenance и лицензии; сохранить изменения отдельными коммитами.
3. Отправить `main` и дождаться нативной матрицы Linux/Windows.
4. Создать `v<версия>` на проверенном коммите и отправить тег. Workflow повторяет матрицу, формирует `SHA256SUMS`, загружает три дистрибутива в draft и публикует release.
5. Проверить tag/commit, latest, состав, скачанные файлы и SHA-256; результаты записать в [validation.md](validation.md).

[Workflow](../.github/workflows/build.yml) запускается также на push `main`, PR и вручную; релиз публикуется только по тегу. Несовпадение версии/тега, отсутствие языковой версии или лишний/пустой дистрибутив блокирует публикацию. electron-builder использует `--publish never`; загрузкой управляет отдельный job через GitHub CLI.

Artifacts хранятся 14 дней, диагностика ошибок — 7. Пользовательские пакеты и серверы в CI не используются.

## Запасной вариант

При недоступном CI штатные сборки можно опубликовать через `gh release create` с результатом генератора notes. Перед загрузкой обязателен `node scripts/release-manifest.mjs`; происхождение локальных артефактов и реальные проверки указываются в описании. Тесты Windows-приложения не заменяют ручную приёмку installer/portable.
