# План монитора Camunda 7

Статус: запланировано 12 ноября 2026 года. Реализация не начата; требуется отдельная отмашка. Публикация и версия выпуска определяются после локальной приёмки.

## Цель и границы

Добавить чтение Camunda 7 REST API с тем же рабочим пространством, что у Flowable: определения, текущие и исторические экземпляры, схема с метками, сведения и переменные, связанные процессы, ошибки, сводка и экспорт. Сохранить существующее поведение Flowable.

Начальная целевая версия — Camunda 7.24. Совместимость с другими версиями подтверждать отдельными проверками. Camunda 8/Zeebe, развёртывание процессов, запуск, изменение переменных, повтор заданий и другие операции управления не входят в объём. Не требовать доступа к базе данных движка.

## Пользовательское поведение

- В подключении доступен выбор Flowable или Camunda 7; адрес, авторизация, секрет и таймаут работают по существующим правилам. Профили Flowable сохраняются без изменения смысла полей. Изменение движка существующего профиля не должно молча переиспользовать несовместимые фильтры и состояние монитора.
- Каталоги: «Определения», Runtime, History и «Инциденты» для Camunda; у Flowable сохраняются dead-letter jobs. Не переименовывать инциденты в задания: это разные сущности.
- Сохранить компактные фильтры и чипы, общий контекст точной версии определения, независимые локальные условия каталогов и переходы назад/вперёд. Показывать только критерии, поддержанные API выбранного движка.
- Схема экземпляра объединяет историю и подтверждённые runtime-позиции. Правая панель сохраняет Runtime/History, единый порядок общих полей и ссылки родителя/дочерних процессов. Открывать точное определение экземпляра, включая старую версию.
- Сохранить выделение, сворачивание панелей, выбор элемента, прокрутку и масштаб при обновлении неизменившихся данных. История по клику раскрывается; фильтрация по элементу выполняется через схему.
- Сводка подчиняется общему сохраняемому переключателю и авторефрешу. Сначала показать схему или XML fallback, затем загружать сводку. Скрытые мониторы не опрашивать.
- Экспорт SVG/PNG переносит метки и их раскладку, не меняя XML/DI. Локальная копия схемы открывается как обычный документ редактора.

## Различия API и данных

Рабочий источник — [REST API Camunda 7.24](https://docs.camunda.org/rest/camunda-bpm-platform/7.24/). Точные поля, фильтры и ограничения фиксировать по результатам стенда.

| Область | Что учесть |
| --- | --- |
| Определения и XML | `/process-definition`, XML выбранной версии; не подменять версию последней |
| Каталоги | `firstResult` / `maxResults`, отдельные count-запросы, соответствие условий списка и количества |
| Текущее состояние | `/process-instance/{id}/activity-instances`: дерево activity/transition instances; учитывать вложенность, параллельность и multi-instance |
| История | `/history/process-instance`, `/history/activity-instance`, исторические переменные; корректно сопоставить состояния, даты и связи вызванных процессов |
| Ошибки | `/incident`, jobs и external tasks; подробности ошибки читать из соответствующего источника |
| Сводка | Проверить `/process-definition/{id}/statistics`; не считать агрегат автоматически эквивалентным нашим счётчикам |

Недоступная история, отсутствие прав, удалённое определение и пустой результат — разные состояния. Недоступность одного источника не скрывает остальные. Конец исторического шага не означает успех; отмену, прерывание и незавершённость отображать без ложного успешного статуса. Не восстанавливать точный пройденный маршрут по косвенным данным, если API его не подтверждает.

Переменные читать без выполнения пользовательских классов и небезопасной десериализации. Сохранить тип, область видимости и различие JSON, сериализованного значения и бинарных данных; отсутствие читаемого значения не выдавать за `null`.

## Технический план

1. Подготовить матрицу соответствия текущих контрактов данным Camunda. Оформить ADR перед изменением архитектуры и контрактов; разделить обязательный общий минимум и возможности движка. Не создавать универсальный компонент со множеством проверок движка.
2. Выделить контракт чтения и выбор адаптера в `src/desktop/runtime`. Реализовать отдельные чтение и декодирование Camunda; существующий FlowableReader сохранить. В `src/shared` оставить контракты без runtime-зависимостей.
3. Ввести явную модель инцидента: тип, BPMN-элемент, экземпляр, execution, время, сообщение и связь с источником ошибки. Не сводить её без потерь к `DeadLetterJob`. Изменения IPC и UI делать совместно, с проверкой отправителя и входных данных.
4. Переиспользовать ограниченный HTTP и хранение секретов: read-only GET, проверка TLS, запрет редиректов, лимит ответа и таймаут подключения. Использовать только разрешённые операции API; доступность расширенных фильтров проверять отдельно.
5. Сохранить общий бюджет времени для сводки, независимые ошибки частей и ограниченную нагрузку. Не обходить все экземпляры ради бейджей. Для исторической выборки исходный ориентир — до 1000 записей, с явной неполнотой `N+` и без обещания полного количества.
6. Сохранить смысл бейджей: runtime и история считают разные экземпляры на элементе, повторы одного экземпляра не увеличивают значение. Инциденты и ошибки имеют явную единицу счёта. Агрегаты Camunda использовать только после проверки эквивалентности; иначе применять ограниченную выборку либо отдельно согласовать другой показатель.
7. Обновить обе локализации, восстановление мониторов, названия и подсказки с движком/подключением. Удаление или смена подключения и поздние ответы не должны смешивать данные разных движков.

## Этапы реализации

| Этап | Проверяемый результат |
| --- | --- |
| 1. Подключение и runtime | Локальный Camunda-стенд, проверка подключения, определения/XML, текущие экземпляры, дерево активностей, задачи и переменные с подсветкой на схеме |
| 2. История и инциденты | Исторические экземпляры и шаги, связанные процессы, инциденты jobs/external tasks, подробности ошибок и корректные переходы |
| 3. Сводка и завершение UX | Проверенные единицы счёта, runtime/history/ошибки в сводке, фильтры, авторефреш, сессии, экспорт и обе локализации |
| 4. Приёмка | Независимые проверки обоих движков, готовая Linux-сборка, ручная проверка пользователя; выпуск только по отдельному запросу |

Этапы — порядок работы, не обещание отдельных публичных релизов.

## Критерии проверки

- Изолированный стенд Camunda 7.24 с фиксированной версией; программно создаваемые тестовые процессы с явной лицензией/provenance. Пользовательские схемы и подключения не включать в Git и артефакты.
- Определения нескольких версий; последние версии по умолчанию; точная версия экземпляра и общий контекстный фильтр.
- Работающий, завершённый, отменённый и приостановленный экземпляры; параллельные ветви, вложенный subprocess, multi-instance, цикл, call activity, асинхронное продолжение и external task.
- Повторы не завышают число разных экземпляров. Несколько incidents на одном элементе, job с нулём повторов, ошибка external task и связь с первопричиной не дают дублирования счётчиков.
- Родитель/дети доступны из runtime и истории, ссылки ведут к правильным экземплярам. Если endpoint не даёт поле, не дополнять его вымышленным значением; дополнительные чтения должны иметь ограниченный бюджет.
- Права на runtime и history проверяются раздельно; тесты без авторизации и с Basic. Bearer проверять на соответствующем тестовом окружении, не объявлять штатным способом Camunda без подтверждения конфигурации сервера.
- Пагинация, фильтры и count согласованы; нет поиска только по загруженной странице под видом серверного. Ограниченная история, очищенные данные, 401/403/404, повреждённые ответы и таймауты не выглядят успешным пустым результатом.
- Схема появляется до сводки; обновление не сбрасывает выбор, масштаб, прокрутку и раскрытые строки. Устаревшие ответы отбрасываются. Вкладки и окна разных движков независимы.
- Для декодеров и счётчиков — unit-проверки; для UI/IPC — fixtures и E2E; для соответствия API — независимый Camunda-стенд. Сохранить регрессионные проверки Flowable, обе темы и локали.
- Перед сдачей реализации: `npm run check`, `npm run test:e2e`, `npm run package:linux` и интеграционные сценарии обоих движков. Проверки Windows выполнять на Windows; macOS остаётся вне объёма.

## Уточнения перед реализацией

Первым этапом подтвердить доступные фильтры и сортировки, форму исторических состояний, учёт переходных активностей и семантику агрегатов на стенде. Если обнаружится существенное отличие UX или счётчиков, согласовать его до реализации соответствующей части. Конкретную patch-версию стенда, набор запросов, лимиты и бюджет параллельности закрепить в ADR и протоколе проверок.
