# 0010. Публичные примеры, лицензирование и локальные пакеты

Статус: принято. Дата: 2026-10-09.

## Контекст

Приложение готовится к распространению как самостоятельный открытый продукт. Встроенные материалы должны иметь проверяемое происхождение и лицензию. При этом разработчику нужна возможность отдельно проверять схемы конкретного пользователя.

## Решение

Собственный код и оригинальные материалы — MIT. Три примера Flowable копируются без изменения XML из `flowable/flowable-examples` на закреплённой revision и остаются Apache-2.0. Две схемы создаются самостоятельно: `flowable-showcase` демонстрирует формы/расширения/развёрнутый подпроцесс, `boundary-events` воспроизводит перекрытие маркера вызова процесса. Их лицензия — MIT. Provenance содержит source, SHA-256, license, сведения об изменении; для upstream также revision. Unit-тест проверяет состав и суммы.

Идентификаторы поставки независимы от организации: Electron `org.bpmndesk.app`, Maven `org.bpmndesk`. Изменение appId создаёт новую идентичность Windows installer; автоматическое обновление старого installer не обещается. Версия 0.2.0 обозначает новый набор примеров и идентичность. `LICENSE`, `THIRD_PARTY_NOTICES.md` и полный текст лицензии примеров включаются в сборки.

Основной набор unit/UI/native/artifact/Flowable-проверок использует только встроенные материалы. Дополнительный пакет состоит из `schemas/` и `provenance.json`; он подключается явно через `BPMN_DESK_EXTRA_SCHEMAS`. `test:extra` проверяет checksum, двойной roundtrip и UI-открытие/сохранение. `validate:flowable:extra` отдельно сравнивает оригиналы с экспортами официальным конвертером. Пакет может храниться вне проекта или в игнорируемом `.local-schemas/`.

Загрузчик проверяет непустой manifest, имена файлов, уникальность без учёта регистра, отсутствие выхода через пути/ссылки, полноту списка и SHA-256. Источники не изменяются. Выходы, traces и отчёты остаются в `.cache/`. Успешный runner записывает receipt с checksum входов/экспортов; независимый конвертер проверяет его перед запуском, чтобы не использовать неполные или устаревшие результаты. Приложение не читает переменную пакета, Vite не импортирует пакет, electron-builder включает только фиксированный `examples/`.

Перед очисткой результатов runner проверяет, что каталоги экспортов и traces не пересекаются с входным пакетом в обе стороны. Проверка учитывает реальные пути существующих ссылок, включая родителей ещё не созданного каталога. Это исключает удаление исходников при ошибочном выборе расположения пакета.

Для схем без DI roundtrip выполняется, UI-проверка явно пропускается. Экспорт для независимой Flowable-проверки создаётся roundtrip-тестом, поэтому отсутствие DI не исключает семантическую проверку. Дополнительный набор не заменяет основной и не запускается неявно.

## Альтернативы

- Обезличивание закрытых схем: сохраняет зависимость от чужого исходного процесса. Выбраны независимые и публичные материалы.
- Подмена `examples/` через переменную окружения: могла бы незаметно изменить основной набор или дистрибутив. Выбран отдельный runner.
- Полностью публичные схемы для всех регрессий: не гарантируют воспроизведение конкретного перекрытия/неполного DI. Для этих случаев нужны оригинальные небольшие примеры.

## Последствия

Скриншоты и desktop-артефакты создаются заново из нового набора. Поддержка пользовательских namespaces сохраняется. Лицензия MIT приложения не заменяет лицензии зависимостей или сторонних схем; watermark bpmn.io остаётся.

История разработки пока сохраняется локально. Перед первой публикацией создаётся один root-коммит очищенного состояния без старых родителей; проверяются все отправляемые ветки/теги. Squash нескольких последних коммитов с сохранением старого родителя не удаляет прежние материалы. Локальные старые объекты/reflog, кеши, пакеты и прежние сборки не входят в публичную поставку. Перенос каталога и публикация выполняются отдельным этапом.
